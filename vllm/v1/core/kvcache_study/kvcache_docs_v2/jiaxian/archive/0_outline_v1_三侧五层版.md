### 第 1 章 · 显存账本：KV Cache 的空间从哪来（~1500 字）

- **本章回答**：HBM 里有多少显存能分给 KV？num_blocks 是怎么算出来的？
- 1.1 HBM 三方分账：权重（常驻）/ 激活（运行期峰值）/ KV Cache（弹性池）
- 1.2 一页多大：`page_size = 2 × block_size × num_kv_heads × head_dim × dtype_size`，以 Llama-3-8B TP2 代入
- 1.3 能买几页：`num_blocks = 可用显存 ÷ page_size ÷ 本 worker 层数`，多卡取 min
- 1.4 实测数字链闭环：num_blocks=13,291 → 13,291×128 ≈ 170 万 KV token 容量（Llama-3-8B pp2tp2 单卡账本）
- 1.5 为什么"实测"而不是配置项：缓存的成本收益权衡

### 第 2 章 · 三侧五层：vLLM V1 管理总架构（~3000 字，全文骨架）

- **本章回答**：vLLM V1 用什么架构同时解决碎片化、共享、分配回收三个问题？NPU 在哪里接入？
- 2.1 三个核心设计决策（先立靶子，后文全回收）
  - 分页管理（PagedAttention）：连续序列切固定 block，解决碎片
  - 逻辑/物理分离：BlockPool 只管 block_id，物理张量在 worker 侧
  - 前缀缓存 + 引用计数：链式哈希定位、ref_cnt 跟踪、LRU 驱逐
- 2.2 三侧架构：配置侧（引擎进程，① 算规格 ② 测预算 ③ 做编排，不碰显存）→ 物理侧（worker 进程，④ 落张量）→ 逻辑侧（引擎进程，⑤ 建逻辑层）
- 2.3 运行期五层（自下而上）：① 物理显存 → ② BlockPool → ③ 单类型管理 → ④ 协调器 → ⑤ 门面 KVCacheManager；Scheduler 是调用者不算层
- 2.4 NPU 的落点：vllm-ascend 插件边界——引擎进程跑平台无关上游代码，`NPUWorker`/`NPUModelRunner` 重写三处（①②④）
- 2.5 衔接契约：一份 `KVCacheConfig` 下发两侧、`block_id == 物理张量行号`、块 0 为 null_block

### 第 3 章 · 启动期：五步装配流水线（~4500 字，全文最重技术章）

- **本章回答**：服务从 `vllm serve` 敲下到第一条请求能进来，KV Cache 池经历了什么？
- 3.0 进程拓扑：1 API server + 1 EngineCore + N × worker（图先行）
- 3.1 ① 算规格：每层产出一个 `KVCacheSpec`（"这一层的 KV 长什么样"的自描述）；worker RPC 遍历 attention 层
- 3.2 ② 测预算：`determine_available_memory` dummy forward 实测
  - NPU 特写一：公式 = 总显存 × 利用率 − 权重 − 激活，**没有图内存项**
  - NPU 特写二：NPUGraph 内存推迟到 capture 后以"建议 `--kv-cache-memory`"日志事后记账
- 3.3 ③ 做编排：同构层合并 → 分组（group_id）→ 算 num_blocks → 多卡取 min 对齐 → 收口 `KVCacheConfig`（平台无关）
- 3.4 ④ 落张量（NPU 主战场，本章最重小节）
  - K/V 各一张独立 int8 字节池（`calc_split_factor` 按维宽比例拆分，等宽对半）
  - 纯 `view` 零拷贝 reshape 成 4D `(num_blocks, block_size, num_kv_heads, head_dim)`
  - 开 P/D KV 传输时 +2MiB 地址对齐切片（buffer 注册要求 dim0=num_blocks）
  - 例外分支：Mamba/hidden-state 层走单张量
- 3.5 ⑤ 建逻辑层：new 13,291 个 `KVCacheBlock`，只装元数据不装数据；块 0 摘作 null_block
- 3.6 启动日志对照：三侧五阶段 × 真实启动日志逐行对账（把日志变成"可读的书"）

### 第 4 章 · 运行期：一条请求的四幕剧（~3500 字）

- **本章回答**：一条请求从入队到释放，KV Cache 的每一块经历什么？（用具体块号讲故事）
- 4.1 入队（第一幕）：预计算链式哈希，全程不碰管理对象
- 4.2 首次调度（第二幕，prefill 一次）：前缀查找只读询问 → 命中块 `touch`（ref_cnt++、移出空闲队列）→ 弹空闲块拼 `block_table` → 写满的块记入哈希表
- 4.3 NPU 写 KV（幕间执行）：清零新块 → `reshape_and_cache` 按 `slot_mapping` 把新 K/V scatter 进双池 → 注意力核按 `block_table` gather 历史
- 4.4 decode 循环（第三幕，每步 0 或 1 块新增）
- 4.5 释放（第四幕）：逆序归还、ref_cnt--，归零才回收；带哈希块排 LRU 队尾受保护、无哈希块排队首优先复用
- 4.6 前缀缓存全景闭环：链式哈希 → touch 共享 → 跨请求积累 → LRU 驱逐保护的完整逻辑链（本章收尾图）

### 第 6 章 · 变奏 B：MLA DeepSeek-V2-Lite（~2200 字）

- **本章回答**：KV 压缩（MLA）会打穿管理框架吗？（答：框架零改动，收益全收在物理层）
- 6.1 MLA 一句话原理：**"头在权重里、cache 存 latent"**
- 6.2 spec 冻结四字段：`block_size=128 / num_kv_heads=1 / head_size=576 / bf16`（576 = kv_lora_rank 512 + qk_rope_head_dim 64）
- 6.3 物理层双池：`V 池装的是 k_rope 不是 value`（全文最反直觉一节，重点讲）——`calc_split_factor([512,64])` 8:1 拆分、value 在 decode 由 latent 经 W_UV 即时上采样
- 6.4 管理框架零改动：页公式包容（147,456 B ≠ FA 公式形态但能算）、逻辑侧五类型逐字同 FA、哈希只看 token 序列

### 第 7 章 · 实证篇：把架构验到比特级（~4500 字，全文差异化亮点）

- **本章回答**：以上架构叙述全是"应该如此"，怎么证明"确实如此"？（稼先读者最买账的章）
- 7.0 实验方法学：打点补丁（每轮 20 行日志）+ 物理归档（一请求一目录、kv_pp{pp}tp{tp}.pt 块-行映射 v2.5）+ 离线检查器（inspectors）+ 横幅对账
- 7.1 **实验一（单机 pp2tp2）**：前缀缓存"零篡改"铁证
  - P 种块 vs R 命中块 [1,2]：全 4 worker × 16 层 K/V **逐位相等**
  - 重算块的 ULP 级差异：b3 vs b4 在 L00 仅 K 2/34816、V 18/34816 位翻转；L15 残差流放大 77%/88%（前缀命中为何必须共享而非重算）
  - 跨八轮实验位级确定、未写槽位全零、flush 平均 39.9ms（异步落盘不影响转发）
- 7.2 **实验二（PD 分离 1P1D）**：一条请求的跨机旅程
  - 哑请求机制：proxy 改写 `max_tokens=1` 发 P、`kv_transfer_params` 从 P 响应注入 D
  - D 侧增量裁剪链（传输量只砍不减语义）+ 尾 token 免传/重算趣谈
- 7.3 **实验三（PD prefix 四象限）**：两个开关矩阵实测（本章招牌）
  - 四象限总表（32.0 vs 64.0 MiB；1.17 vs 1.46 ms；跨请求显存驻留差异）
  - 四条铁律：P 开关只管"算多少"、D 开关只管"传多少"、P 恒全量上报、正确性全等
  - 结构性解释：哈希盐进程级随机（os.urandom(32)）→ 双侧独立哈希空间 → 解耦的结构前提
- 7.4 **实验四（可视化）**：kv_visualizer 工具（Vue3 + FastAPI，7 标签页，A~D 60 项核验）——把冷数据做成可交互探索

## 七、数据点弹药库（实测数字单点核对清单）

> 写作时从此处取数；每个数字必须能在素材原文中找到出处（标号即来源调研时核过的事实）。

- **Llama-3-8B 主线**：13,291 blocks；每层每 worker K/V `(13291,128,4,128)` bf16；TP2 后 page 32KB；就绪 ~50s
- **GDN Qwen3.5-4B**：block size 16→128→1024；混合部署 5 个特有行为；对齐后每 worker 16 层
- **MLA V2-Lite**：147,456 B/层/块；31,104 B/token（27 层×576×2B）；13,013 块；1,665,664 token；8.89×；双池 8:1=(1.125,9.0)；命中 61.3%→68.9%（2688/3900）；
- **实验一（单机）**：4 worker × 16 层逐位相等；L00 重算差异 K 2/34,816 / V 18/34,816（Pearson≈1.000001）；L15 残差放大 77%/88%；[KVS] 20 行/轮（v2.1→v2.5 精简 26 倍）；flush 均 39.9ms；八轮位级确定
- **实验二/三（PD）**：block 128 tok；req_p 324 → req_r 486（块 1,2=256 共享 + 块 4,5 新增）；增量 32.0 MiB vs 全量 64.0 MiB；第二请求 KV transfer 1.17ms（q1）vs 1.46ms（q2）；首请求 260.75~309.37ms；`max_tokens=1` 哑请求是 P 的硬要求
- **契约类数字**（无单位，作为"架构契约"叙述）：block_id 从 0 编号 == 物理行号；block 0 为 null_block；spec 冻结四字段；管理框架零改动（MLA）
