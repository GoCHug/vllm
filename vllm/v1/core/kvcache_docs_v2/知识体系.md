# KV Cache 子系统知识梳理方案（待审定稿）

> 按三个专业问题组织：**整理出什么**（产出物）→ **从哪些方面**（知识地图）→ **有哪些阶段**（执行计划）。
> 两条总原则贯穿始终：
> 1. 通用机制只在一处讲（基准 = 纯 Full Attention 单机场景），场景差异只记"变了什么"；
> 2. 每个知识点四位一体：**图 + 文 + 代码锚点 + 不变量**，缺一不算完成。

---

## 一、需要整理出什么（四层产出物）

知识分四层，每层回答一类问题，缺一层体系就不完整：

| 层 | 回答的问题 | 产出形式 | 验收标准 |
|---|---|---|---|
| **L1 概念层** | 这是什么、为什么需要 | 总览、术语表、心智模型（块模型一图流） | 新人 30 分钟能复述核心抽象 |
| **L2 机制层** | 原理怎么运作 | 按维度分章：每章 = 总图 + 机制正文 + 不变量清单 | 每章通过自己的"讲完标准"（见§二） |
| **L3 实现层** | 代码里在哪里 | 源码地图（文件→职责）、端到端调用链注释 | 任何论断能跳到 `文件:行号` |
| **L4 应用层** | 怎么用、怎么排障 | 参数总表、场景速查、误区自测、调优指引 | 常见问题可查阅定位，不必重读机制 |

> **层级关系**：L1 建立共同语言 → L2 是主体 → L3 把 L2 钉在代码上 → L4 让体系可被消费。
> 现有散材料的归类：大多落在 L2（机制）；L1 零散、L3 只有个别行号、L4 几乎没有——这就是"乱"的量化描述。

## 二、从哪些方面（五维知识地图）

机制层（L2）沿五个维度切分，每维回答一个核心问题：

```
维度一 · 内容（存什么）── 由模型结构决定
维度二 · 空间（存哪里）── 由系统决定
维度三 · 生命周期（怎么管）── 块是资源
维度四 · 时间线（何时做）── 启动期装配，运行期消费
维度五 · 场景（怎么变）── 横切：配置不同，前四维如何变
```

依赖关系：

```
0 块模型（共同语言）
 ├─▶ 维度一 → 维度二 → 维度三 → 维度四（逐层依赖）
 └─ 维度五 横切全部：只记差异，不重复讲机制
```

### 0. 根基：块模型（共同语言，先于一切）

- 0.1 为什么需要 KV Cache：自回归重算的 O(n²) 代价、时间换空间
- 0.2 为什么要分页：连续分配的浪费与碎片 → PagedAttention（虚拟内存思路）
- 0.3 块模型抽象：逻辑序列 →（`block_size` 切）→ 逻辑块 →（`block_table`）→ 物理页；
  `block_id` = 逻辑↔物理的唯一桥梁（调度只认编号，kernel 只认行号）
- 0.4 四个基本量：`block_size`（块容量）/ `page_size_bytes`（块字节）/ `num_blocks`（池容量）/ `block_table`（翻译器）

### 维度一 · 内容：存什么（模型决定块里装什么）

- 1.1 三种缓存家族（最小内存单元）
  - 1.1.1 Full Attention：每 KV 头存完整 K/V，字节 ∝ token 数
  - 1.1.2 MLA：每 token 一个压缩 latent（无 head 维）
  - 1.1.3 Mamba / GDN：一份就地更新的递归状态（字节固定）
- 1.2 Spec：块格式的描述体系
  - 1.2.1 核心三量：`block_size` / `page_size_bytes` / `storage_block_size`（谁决定、随什么变）
  - 1.2.2 继承树（两大继承支）与根 Spec 对比
  - 1.2.3 `page_size_bytes` 公式汇总与换算
- 1.3 块内容的变体
  - 1.3.1 格式变体：Diff-KV、量化（FP8/INT8/INT4/NVFP4/TurboQuant）、stride 布局（HND/NHD）
  - 1.3.2 语义变体（布局不变、驻留策略不同）：sliding window / chunked / sink / cross / RSWA / encoder-only
- 1.4 逻辑→物理换算：`seq_len → num_blocks × block_size`；三种 K/V 打包形式 + `block_dim` 索引

**讲完的标准**：给任意模型，能算出每层块内容、`page_size_bytes`、物理 shape。

### 维度二 · 空间：存哪里（系统决定页怎么落、卡怎么分）

- 2.1 物理页的物化
  - 2.1.1 int8 底座 → reshape（普通 / padding / packed）→ 零拷贝视图 → bind 给层
  - 2.1.2 shape 来源（后端 `get_kv_cache_shape()` + stride order）；为何 int8、何时转 dtype
- 2.2 并行下的分布
  - 2.2.1 PP 按层切；2.2.2 TP 按 KV 头切；2.2.3 DP 容量语义；2.2.4 CP/DCP 块表分片（Mamba 不切）
  - 2.2.5 一致性约束：同层 spec 跨 TP rank 必须等值
- 2.3 混合模型的页字节统一
  - 2.3.1 四条路线：已是 max / Mamba padding / 能整除放大 `block_size` / attention stride padding
  - 2.3.2 分组机制：spec 值相等聚组、`group_size` 确定、交错拆组
- 2.4 物理布局两条路线
  - 2.4.1 通用多张量（一层一页，`shared_by`）；2.4.2 Packed（一组一片，`block_stride`）
  - 2.4.3 一个 `block_id` 占多少字节：三分支账

**讲完的标准**：给任意部署（pp×tp、是否混合），能画出每张卡的层分布、张量形状、块落点。

### 维度三 · 生命周期：怎么管（块作为资源）

- 3.1 管理架构（静态骨架）
  - 3.1.1 五层结构：Manager（门面）→ Coordinator（跨组）→ SingleTypeManager（单组）→ BlockPool（池）→ 物理张量
  - 3.1.2 九个核心数据结构：`KVCacheSpec / GroupSpec / KVCacheTensor / KVCacheConfig / KVCacheBlock / FreeKVCacheBlockQueue / BlockHash / BlockHashToBlockMap / BlockPool`（职责与不变量）
- 3.2 块的生命周期：分配 / 释放（逆序、`ref_cnt`）/ 复用（前缀命中）/ 驱逐 / 抢占（重算）；CoW 与共享
- 3.3 BlockPool 内部：`null_block`、空闲队列、分配回收铁律、驱逐顺序
- 3.4 前缀缓存：`BlockHash` 三级演变、命中判定、满块写回、幂等、约束条件
- 3.5 管理的产物：`block_table`、`slot_mapping`、computed blocks、watermark 语义

**讲完的标准**：给任一操作，能说出块的状态迁移、执行组件、保证的不变量。

### 维度四 · 时间线：何时做（把维度一~三织成两条时间线）

- 4.1 启动期：算规格 → 测预算 → 做编排（合并/分组/投影/算块数/对齐）→ 物化 → 装配管理层 → 预热
- 4.2 运行期（一条请求的一生）：准入门控 → 前缀命中 → 两阶段分配 → prefill/decode/chunked → 释放/抢占/驱逐
- 4.3 写路径：新 token → `slot = block_id × block_size + offset` → kernel 写
- 4.4 读路径：`block_table` → `block_id` → 张量 `block_dim` 维索引（三族统一）
- 4.5 调度器↔Worker 协作：记账（Engine）→ 广播 block_ids → 各卡本地解释；CPU↔GPU 同步点
- 4.6 观测指标：KV 使用率、前缀命中率

**讲完的标准**：给任意时刻，能说出系统在做什么、哪些状态在迁移。

### 维度五 · 场景：怎么变（横切，只记差异）

| 场景变量 | 改动的格子 | 核心差异一句话 |
|---|---|---|
| 并行配置（pp/tp/dp/cp） | 2.2、4.1 | 页切分与跨卡对齐方式随拓扑变 |
| 混合模型（Qwen3.5 类） | 1.1、2.3、2.4、3.1、4.2 | 多一族状态页、需统一页、分组双块表、常驻状态块 |
| prefix caching 开关 | 3.4、4.2 | 命中/写回是否生效；与 DP 的交互 |
| 量化 KV | 1.3.1、2.1 | 字节与布局变，管理逻辑不变 |
| 投机解码 / MTP | 1、4.2 | 额外预留块；Mamba 环缓存 |
| offload / connector | 3.2、4.2 | 外部 computed tokens 参与分配 |
| encoder-decoder | 1.3.2、4 | CrossAttention 页不释放；encoder 预算 |

## 三、有哪些阶段（六阶段执行计划）

| 阶段 | 目标 | 主要动作 | 产出 | 通过标准 |
|---|---|---|---|---|
| **S1 骨架定稿** | 统一框架与语言 | 审定本方案（维度、命名、边界） | 定稿大纲 | 无争议格子 |
| **S2 概念对齐** | 建立共同语言 | 术语表、块模型总览、心智模型 | L1 概念篇 | 任何人用同一套语言能讲清核心抽象 |
| **S3 机制填充** | 主体内容 | 按维度一→二→三→四逐章：先总图、后机制、列不变量 | L2 四章 + 四张总图 | 各维度通过自己的"讲完标准" |
| **S4 实现锚定** | 文对码 | 全部论断核对源码（`文件:行号`）、源码地图、端到端调用链 | L3 地图 + 调用链篇 | 任意论断可跳转代码 |
| **S5 应用补齐** | 可用可查 | 参数总表、场景速查（维度五成文）、误区自测、调优指引 | L4 应用篇 | 常见问题可查阅定位 |
| **S6 收束评审** | 一致性 | 交叉引用审计、去重（机制只讲一处）、图示风格统一 | 最终知识库 | 无双写、无死链、术语一致 |

**阶段说明**：

- **S3 是主战场**，严格按依赖序做：维度一未完成不进维度二（空间依赖内容）；每章的总图与 `现有材料`（散文档、drawio）先做归位复用，不重写已有内容；
- **S4 必须逐条过**：没有代码锚点的机制描述一律补锚点或删除；
- **S5/S6 可与 S3 交叉进行**：发现参数、误区随手登记，最后统一成文。
