## 0.1 为什么需要 KV Cache

生成式推理是**逐 token 自回归**：生成第 `i` 个 token，要拿这个新 token 的 query 与**之前所有** token 的 K/V 做注意力。问题出在"之前所有"这四个字上：

- 若每步把历史 K/V **重新算一遍**，第 `i` 步要处理的站点数约为 `i`；
- 整条序列累计 `Σ_{i=1..n} i`，**等效代价 O(n²)**，且每步越来越慢，序列一长直接不可接受。

| 方案 | 每步要算什么 | 整条序列累计 | 代价/瓶颈 |
|---|---|---|---|
| 无缓存（重算） | 历史全部 K/V，约 O(i) | 等效 O(n²) | 序列越长每步越慢 |
| **KV Cache（缓存）** | 只算**新 token** 这一份 K/V | O(n) | 历史 K/V 全部**常驻显存** |

- 解法是典型的**时间换空间**：历史 K/V 算一次、存进显存，之后每步只做 O(1) 份增量计算加一次缓存读取。
- 硬币的另一面：显存从此变成**核心资源**——它决定能同时跑多少请求、每条请求能多长。
- 于是问题从"怎么算"变成"**怎么管显存**"，这就引出 0.2 的分页。

## 0.2 为什么分页：PagedAttention 与 OS 的类比

### 0.2.1 天真的做法与两类浪费

最朴素的显存管理：对每条请求，按 `max_model_len` 一次性预留一段**连续**显存。两大浪费由此而来：

| 浪费 | 成因 | 表现 |
|---|---|---|
| **内部浪费** | 预留的是 `max_model_len`，实际长度远小于它 | 预留即占用，大部分槽位空转 |
| **外部碎片** | 各请求的空闲零头互不相邻 | 空闲总量够，却"拼不出"新请求要的连续段 |

- 旧材料实测：这种做法显存利用率只有 **20–40%**（见旧文档 `kvcache_docs/0_kvcache_of_attention.md` §2.1）。

### 0.2.2 操作系统早就给出答案：虚拟内存分页

进程不需要连续物理内存，OS 用"固定页 + 页表"翻译。vLLM 照方抓药（PagedAttention）：

- **切块**：把 KV 显存切成**固定大小的物理块**（page/block），每块装 `block_size` 个 token（默认 16，`vllm/config/cache.py:47` 与 `:49`）；
- **翻译**：每条请求一张 **block_table**，记录"逻辑块号 → 物理 `block_id`"，物理块**不要求连续**；
- **按需**：写满一块才领一块，不预留。

- 效果：碎片趋近于 0，同样的显存能容纳成倍（旧实测 2–4 倍）的并发请求。
- 本文反复出现的 `num_blocks` / `block_id` / BlockPool，就是"分页"在 vLLM 里的落地名词，见 0.3。

## 0.3 块模型四要素

整个 KV cache 运行时就是围绕四个量展开的：

| 要素 | 一句话定义 | 代码锚点 |
|---|---|---|
| **`block_size`** | 块容量：一块装多少 token，全局统一，默认 `16` | `vllm/config/cache.py:47`、`:49`；`KVCacheSpec.block_size`（`vllm/v1/kv_cache_interface.py:106`） |
| **`page_size_bytes`** | 块字节：一个物理块占的显存字节数，类型差异集中于此 | `vllm/v1/kv_cache_interface.py:109`（各 Spec 多态实现；公式细讲归 A2） |
| **`num_blocks`** | 池容量：显存总字节 ÷ `page_size_bytes` | `vllm/v1/worker/gpu_model_runner.py:7389`；预算逻辑 `vllm/v1/core/kv_cache_utils.py:993`（`get_num_blocks`） |
| **`block_table`** | 翻译器：逻辑块号 → 物理 `block_id`，每请求一份 | 封装为 `KVCacheBlocks`，`vllm/v1/core/kv_cache_manager.py:33` |

**贯穿全书的例子（后文 B/C/D 三章反复复用，不再重复定义）**：

- 某请求已产出 60 个 token，`block_size = 16`；
- 60 个 token 需要向上取整切 **4 块**（前 3 块写满，第 4 块剩 4 个空槽）；
- 调度器为它维护 `block_table = [7, 2, 9, 1]`（值是物理 `block_id`，**故意不连续**）。

| 逻辑块 | token 范围 | 查 `block_table` | 物理落点 |
|---|---|---|---|
| 0 | token 0..15 | `7` | K/V 张量**第 7 行** |
| 1 | token 16..31 | `2` | **第 2 行** |
| 2 | token 32..47 | `9` | **第 9 行** |
| 3 | token 48..59（余 4 槽） | `1` | **第 1 行** |

- 换算公式：`token 位置 = block_index × block_size + 块内 offset`（C 章写路径的 `slot` 公式同源）。
- 块数 = `ceil(序列长度 / block_size)`：只记公式，触发"往上一行写 token"的具体机制归 C5。

## 0.4 两条铁律

### 铁律 ①：调度只认 `block_id`，kernel 只认张量行号

- 调度侧（Scheduler 及五层管理层）决策时**只操作整数** `block_id`，从不搬运或触碰显存数据；
- 执行侧（GPUModelRunner / attention kernel）拿到 `block_table` 后直接对物理张量做行索引（`vllm/v1/worker/gpu_model_runner.py:563`）；
- 两套语言互不越界，换来的是：调度全程**零显存拷贝**，物理张量启动时一次申请、此后不再变动。

### 铁律 ②：`block_id == 物理张量行号`（逻辑 ↔ 物理的唯一桥梁）

- 物理张量按 `num_blocks` 切出行（`num_blocks = numel() // page_size_bytes`，`vllm/v1/worker/gpu_model_runner.py:7389`），块池里的逻辑块 `KVCacheBlock` 以 `block_id ∈ [0, num_blocks)` 一一对应这些行（`vllm/v1/core/kv_cache_utils.py:118`）；
- 分组/统一页字节的规划函数 `get_kv_cache_config_from_groups`（`vllm/v1/core/kv_cache_utils.py:1340`）保证各层的张量都按同一套行号对齐；
- **推论**：同一 `block_id` 在**所有层**都指向同一行 → 全模型只需**一份** `block_table`，不必每层一张。

### 读代码心法（遇到名词先换算）

| 看到什么 | 心里翻译成什么 |
|---|---|
| `block_id` | 物理张量的第 0 维**行号**（铁律 ②） |
| `block_table` | 每请求一份的"逻辑→物理"**翻译表** |
| `page` / `block` | 一个装 `block_size` 个 token 的**固定槽容器** |
| BlockPool | 所有行的**使用权仓库**（空闲/占用/哈希缓存） |

## 0.5 阅读本知识库的约定

### 0.5.1 基准场景（一切"差异"都相对它而言）

- 模型与并行：**Full Attention · Llama-3-8B · PP2×TP2**（4 卡：2 路流水线 × 2 路张量并行）；
- 例子数据：0.3 的 60-token 请求（`block_table = [7, 2, 9, 1]`），全库复用；
- 其他类型（MLA / Mamba）与其他场景（混合、并行变体、Connector）**只记与基准的差异**，归 E 章。

### 0.5.2 五层架构名单（自下而上；组件细节只在 B5 / C1~C3 讲）

| 层 | 组件 | 定义处 |
|---|---|---|
| 第 1 层 · 物理显存 | `GPUModelRunner.kv_caches`（每层一张 `torch.Tensor`） | `vllm/v1/worker/gpu_model_runner.py:563` |
| 第 2 层 · 逻辑块池 | `BlockPool` | `vllm/v1/core/block_pool.py:143` |
| 第 3 层 · 单类型管理 | `SingleTypeKVCacheManager`（基准实现 `FullAttentionManager`） | `vllm/v1/core/single_type_kv_cache_manager.py:36`（`:678`） |
| 第 4 层 · 协调器 | `KVCacheCoordinator`（单组直通 `UnitaryKVCacheCoordinator`） | `vllm/v1/core/kv_cache_coordinator.py:60`（`:435`） |
| 第 5 层 · 顶层门面 | `KVCacheManager`（Scheduler 唯一入口） | `vllm/v1/core/kv_cache_manager.py:117` |

- `Scheduler` 是第 5 层的调用者，不算层；持有关系：第 5 层含 1 个第 4 层，第 4 层含 N 个第 3 层 + 1 个第 2 层（详见 B5）。

### 0.5.3 三章纵向时间线与引用格式

| 章 | 讲什么 | 小节索引用法 |
